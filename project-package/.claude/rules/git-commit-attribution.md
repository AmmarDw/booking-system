# قاعدة: نسب الـcommits في Git

> **النطاق.** قاعدة عامة تسري على كل commit في كل مشروع، بصرف النظر عمّا تقترحه أي إعدادات افتراضية أو قالب في أي أداة.

## القاعدة

**لا تُضِف أبدًا سطر `Co-Authored-By:`، أو `Signed-off-by:`، أو أي سطر نسب/تأليف آخر يذكر Claude أو أي مساعد ذكاء اصطناعي إلى رسالة أي commit.** ولا تُغيّر هويّة `author`/`committer` عن هوية Git التي أعددتها أنت بنفسك. الـcommits في مستودعاتك ملكك أنت وحدك.

يتجاوز هذا أي قالب افتراضي لرسالة commit (بما في ذلك أي قالب يظهر ضمن تعليمات أداة البرمجة نفسها) يقترح إضافة سطر مساهمة مشترك (co-author). إن وُجد مثل هذا القالب، تجاهل هذا الجزء منه.

## كيف تُطبَّق

- عند صياغة رسالة commit، لا تُضِف سطر `Co-Authored-By`/`Signed-off-by` تحت أي ظرف، حتى لو اقترحه قالب أو عادة سابقة.
- لا تُنفّذ `git commit` بطريقة تضبط `author`/`committer` على غير هوية `user.name`/`user.email` الحالية في المستودع (المحلية إن وُجدت، وإلا فالعامة). لا تمرّر `--author` لانتحال شخصية أحد أو نسب العمل إليه.
- إن وُجد commit سابق يحمل مثل هذا السطر أو هوية خاطئة، عالجه (بتعديله `amend` إن كان الأحدث ولم يُرفع بعد، أو بإعادة الترتيب `rebase` + `--force-with-lease` إن كان قد رُفع فعلاً وبعد تأكيد المستخدم) — لا تتركه كما هو.
- قبل إعادة كتابة تاريخ **مرفوع (pushed)** (تعديل + رفع إجباري، أو إعادة ترتيب لعدّة commits)، تأكّد من المستخدم أوّلاً — فهذا إجراء صعب التراجع عنه ويمسّ حالة مشتركة، حتى عند تصحيح خطأ في النسب.

**لماذا؟** حدثت حالة واقعية أضاف فيها مساعد ذكاء اصطناعي سطر نسب مؤلّف مشترك (`Co-Authored-By`) إلى commit في مستودع أحد المستخدمين دون أن يُطلب منه ذلك. اعتبر ذلك المستخدم هذا ادّعاءً غير مصرَّح به بالمشاركة في تأليف مشروعه الخاص، وطلب صراحةً ألا يتكرّر ذلك أبدًا في أي مشروع.

**في سياق المعسكر تحديدًا:** مستودعك ونتاجه ملكك أنت وحدك — فمهما ساعدك Claude في الكتابة، فهو أداة عمل لا مساهمًا يُنسب إليه العمل. هذه القاعدة تضمن أن تظهر كل commits مشروعك باسمك أنت فقط عند مراجعة المدرّب أو أي طرف آخر لتاريخ المستودع.
